# Recovery, replacement and retirement

The local `.ovault` is a private owner capability, encrypted with AES-256-GCM. A random 16-byte salt and 12-byte nonce accompany scrypt N=32768, r=8, p=1, 32-byte output (approximately 32 MiB working memory). The authenticated header fixes KDF parameters and format. Parameters cannot be changed by an input to force arbitrary KDF work. This is a measured laboratory choice, not a claim of adequate protection for every password or device. Use a separate high-entropy passphrase. Weak passphrases remain vulnerable to offline guessing. [scrypt specification](https://www.rfc-editor.org/rfc/rfc7914).

The decrypted vault contains owner seed, creator shares, ciphertext, signed manifest, provider pins/addresses, retained receipts and per-witness observation anchors. Private vault files use mode 600; writes and directory updates are fsynced. An advisory per-vault file lock serialises cooperating local CLI processes. This does not provide secure memory erasure, keychain integration, protection from local malware, rollback-resistant hardware or distributed locking across cloned devices. The passphrase is prompted or supplied through a trusted client-only environment variable, never a command argument or SaaS API. The lab generates a client passphrase in the ignored mode-600 `.env05`; that shared host is trusted.

`backup` creates a separate encrypted copy; export it to independently retained storage and keep the passphrase independently available. The lab's `/recovery` volume demonstrates isolation from SaaS mounts, not protection from loss of the shared Docker host. `restore` authenticates the backup, validates the owner/manifests/pins and creates a fresh vault path. The CLI also requires its public `--trust` configuration; the experiment retains that file separately. On complete device-file loss, retain an independent copy or extract the authenticated `trust` object from the encrypted backup using the trusted vault decoder before invoking the CLI. Do not bootstrap replacement identities from a SaaS account response. A replacement client then obtains challenge-bound signed status from independent witnesses. The mandatory scenario restores a backup made **before the latest accepted check-in**, demonstrating that current retained presence is recovered rather than invented from an application database or a fresh backup.

Restoration clones authority. It does not revoke a lost/stolen unlocked device. The test retains the old kit, signs a second check-in from it after replacement and confirms that signature still works. Passphrase change/re-encrypting a vault likewise does not revoke copied signing keys. Losing the only vault/backup or its passphrase prevents owner signing/recovery; account control cannot replace it. No administrative bypass is added.

The bounded rotation mechanism is explicit retirement: use the old capability to obtain a three-witness disarm **before irreversible closure**, persist that result, then create and arm a **fresh Capsule**, with new owner seed, encryption key/nonce, manifest, payload and policy commitment. The CLI `rotate --out NEW.ovault` performs those steps using the same public protocol. Old signatures do not verify for the new commitment. Old-Capsule retirement and new-Capsule arming are not atomic: if new creation fails, the old Capsule remains disarmed; retry creating a new Capsule. If the old capability is gone, stolen, or closure already began, in-place revocation is unavailable and rotation cannot promise cancellation of the old operation.

Material previously exposed by a 0.4-style client is treated as compromised permanently. Neither upgrading software nor rotating a signing key can make an operator forget plaintext, an encryption key or custody shares it already saw. A fresh 0.5 Capsule with new local encryption establishes a new boundary; it does not retroactively secure old content. A stolen active device can race retirement, including denial of service or closing opportunities; there is no remote wipe or hardware attestation in this generation.

After one witness process restarts, it must complete the inherited owner-authorised, fresh-target-challenge, three-peer state-transfer repair before signing/inspection for that Capsule. The Hostile SaaS experiment repeats check-in while that process is stopped and inspection after restart/repair. Committee-wide cold restart, identity replacement and custodian repair remain unsupported and fail closed; the older limits are preserved rather than hidden behind account recovery.
