# Generation 0.5 — The untrusted operator

The experiment separates an adversarial consumer operator from an independently trusted creator installation. It does not assert that operator-delivered JavaScript can protect secrets against the operator delivering that code. The creator CLI, operating system, local verification toolchain, dependency supply chain, passphrase entry and independently obtained provider trust configuration are explicit roots of trust.

## Adversary and independent principals

The SaaS operator controls Laravel, its database, backend courier, deployment, HTTP responses and JavaScript. It may read everything submitted to those services, fabricate UI success, censor/delay/replay/reorder requests, substitute public projections and serve malicious code. It retains every key/plaintext exposed by earlier clients forever. It does not automatically possess the independently installed creator's signing seed, memory, local vault/passphrase, independently authenticated trust pins, witness keys or custody shares.

Witnesses retain the generation-0.4 static N=4/P=3/A=3/f=1 protocol. Its fault, clock, durable-lock, finite-schedule and repair limitations still apply. Custody has a separate trust model: the reference provider is static 2-of-3 shares, with no cryptographic policy enforcement against two colluding holders. Four containers are not four independent organisations. The shared Docker host is trusted for these experiments; a host administrator/Docker-daemon compromise violates the isolation assumptions. No Docker socket or owner recovery volume is mounted into SaaS services.

## What changes

`Untrusted.client.Client` runs locally and invokes the same public wire-v4 manifest, evidence, arm/disarm, retention, repair and release APIs. It generates the owner key and AES-GCM Capsule locally and signs before submitting. It never sends the capability kit to Laravel or a signing backend. Custody enrollment shares go directly to the respective pinned provider, never through the SaaS courier. The local creator necessarily knows its own plaintext and shares. Plaintext is fixed synthetic content; delivery is simulated.

An independently obtained trust configuration pins provider public keys and endpoint URLs. A response from the SaaS cannot redefine those pins. Initial trust-file generation in the lab uses the isolated direct network; that is not a production authenticated directory. In a deployment, fingerprints/configuration must be authenticated through an independent channel. Generation-0.5 provider endpoints require TLS. The local lab generates seven hostname-checked provider certificates under an independently retained test CA; each private provider TLS key is mounted only into its provider, and SaaS receives only the public CA certificate. Custody enrollment therefore crosses certificate-verified TLS even in the hostile lab. HTTP remains only for the internal/public-material SaaS courier. The test CA/private-key provisioning is local laboratory infrastructure, not a production PKI or independent-administration demonstration. Transport identity authentication and pinned protocol signatures have distinct purposes.

`Consumer05` is a separate Laravel integration, preserving the earlier consumer. It accepts only a bounded public projection (manifest, ciphertext, public receipts), rejects private-capability fields and optionally relays signed witness messages. It has no create-key, encrypt-secret, upload-private-kit or signing flow. Its page labels itself operator-controlled; **it cannot authenticate its own JavaScript, installation instructions or account identity**. A dishonest UI may still lie successfully. Trusted confirmation occurs in the installed client, not in that page.

## Fresh authoritative observation

Generation 0.4 signed acknowledgements are portable historical evidence, not proofs of current state. The additive `/inspect` request supplies a fresh random 256-bit challenge and Capsule ID. Each pinned witness signs version 5, kind INSPECT, Capsule ID, immutable manifest hash, challenge, witness index, complete locally retained records and healthy clock interval. The client verifies every envelope and contained record, checks previously retained per-witness record hashes are not removed, and requires three distinct responsive endpoints. It does not count a SaaS success boolean as a receipt.

Python and an independent Node verifier check envelope signatures, full committed manifest semantics, challenge/source/domain/clock schema. Existing independent Python/Node receipt and release verifiers remain unchanged. A fresh challenge prevents a cached old response from satisfying a new request. The local encrypted vault stores anchors and receipts. Fresh status is a read sampled during the challenge round, not omniscient knowledge of events committed after that read or proof that clocks show objective UTC. Concurrency, network delay and the existing fault assumptions still matter. Losing quorum produces an error/unknown result, never a confident stale status.

## Authorisations, replay and independent routing

Arm, check-in and disarm retain their existing manifest/operation/contract/challenge/signature binding. An old command cannot authorise a new Capsule or a new check-in slot; a closed/disarmed Capsule cannot be silently re-armed. Identical retries remain intentionally idempotent. A captured authentic DISARM is a valid authorisation for that same Capsule until its closure semantics forbid it; the system does not provide revocation of an individually signed but undelivered command. No new generic bearer authorisation, account-reset signature or administrator recovery grant exists.

The SaaS courier is optional. A creator can inspect a relayed response, reject substitution or false success, and submit directly to independent witness URLs. Censorship through the courier **succeeds at that path**; recovery depends on an alternative reachable path. If all independently reachable paths are blocked, the system cannot ensure timely acceptance. Likewise a SaaS-operated release worker can be withheld; an independently run worker/client can evaluate and request simulated delivery. The protocol does not magically schedule that independent worker.

## Client distribution and updates

The supported experimental client is a locally built/pinned CLI image, installed from an independently reviewed source copy. `Untrusted.install_check` records hashes of client/core/verifier sources, Dockerfile and pinned Python requirements. An expected manifest digest must be authenticated independently of the SaaS, and checked using an already trusted toolchain. Obtaining a digest and the verifier from the same compromised operator is not authentication. Source hashes do not attest a compiler, Docker daemon, base image, wheel, runtime memory or signed-release process.

There is no auto-update endpoint, downloaded-code execution, SaaS plugin loader or code fetched as part of a creator action. Update by reviewing a new source/dependency manifest and independently authorising a new installation. Base-image digests are recorded in build output but the reference Docker tags are not a reproducible-build/security-update system. Signed release governance, notarisation, device secure boot, hardware-backed signing and supply-chain review remain unimplemented. The retained malicious-code experiment intentionally executes hostile JavaScript with a synthetic accessible capability and proves it can steal the key and disarm; the protocol cannot distinguish that signature from a legitimate creator's signature.

## Guarantees and boundaries

Established by the bounded experiments: SaaS account/backend control alone does not produce a valid creator signature; changes to locally committed content/policy/destination are rejected; false acknowledgements cannot satisfy the trusted verifier; old fresh-status envelopes cannot answer a new challenge; independent routes and a retained owner capability permit operation without the SaaS; untrusted courier use does not change policy semantics.

Not established: production security, anonymity, availability under arbitrary censorship, secrecy from compromised creator devices or already exposed keys, independent-host/organisation trust, reliable UTC, hardware power-loss durability, cryptographically enforced custody, committee-wide cold restart, in-place identity rotation or secure automatic client updates. A successful signed check-in still authenticates an entity's assertion, not the fact of biological life.
