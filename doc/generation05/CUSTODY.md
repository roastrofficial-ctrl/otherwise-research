# What changes custody security—and what does not

Generation 0.5 moves creator-held secrets out of the SaaS. It does **not** turn the reference custody implementation into cryptographic conditional release. Its descriptor continues to advertise `cryptographic_policy_enforcement=false`; requests for stronger enforcement remain incompatible.

## Retained executable attack

The hostile test gives two deliberately malicious custodians access to their own stored shares (a capability-protected laboratory export route, excluded from any production claim). `Shamir.combine` recovers the AES key and AES-GCM decrypts the synthetic Capsule **while the honest protocol still reports release unauthorised**. No forged certificate, broken cipher or compromised witness is needed. This regression must remain successful. The SaaS alone does not receive those shares in 0.5; a custodian quorum is a different adversary.

For this specific static-share design, the limitation is direct: if a set of parties already holds enough information to run an unconditional reconstruction algorithm, policy validation in their server software cannot stop them from running that algorithm early. This is not a theorem that every future conditional cryptographic design is impossible. It identifies the missing assumption: enough decryption capability must remain unavailable to the adversary until the condition is established.

| Alternative | What could improve | Remaining trust and failure boundary | 0.5 status |
|---|---|---|---|
| Independent organisations holding static shares | SaaS compromise alone no longer gathers the threshold; administrative separation reduces correlated compromise | At least enough holders must keep shares secret and follow policy; collusion still reconstructs early; some can withhold | Shipped laboratory share model, not independent-host validation |
| Witness-gated threshold key release / MPC | Custodians alone may lack the full required capability; independent witnesses can contribute only after validating a certificate | A sufficient coalition across the new groups, compromised key generation or faulty policy/time observations can still violate the condition; threshold honesty remains | Design only; no new threshold-cryptography security claim |
| HSM/TEE-enforced release policy | Device-internal keys may resist an application/server administrator; independently verified attestation could bind policy code | Trust hardware/firmware/vendor roots, attestation, secure time and anti-rollback; availability and supply-chain attacks remain; an arbitrary HSM API is not conditional enforcement | Design only; no hardware deployed |
| Future public randomness / timelock encryption | A future beacon value can make decryption capability unavailable before a designated round | Beacon threshold/cryptographic assumptions; designated time is not a revocable absence contract; withholding and retained old ciphertext matter | Design only |
| Time-delay puzzles / sequential work | Can impose a computational delay under a stated speed assumption | Delay is not proof of missed check-in; faster hardware, setup assumptions and changing schedules matter; cannot retract already available capabilities | Design only |
| Witness encryption / more ambitious predicate encryption | Might tie decryption to a witness for a formal statement under stronger assumptions | Practical construction and precise assumptions need separate research; the statement still needs an authenticated real-world observation/time source; no claimed implementation | Research boundary only |

The [drand tlock implementation](https://github.com/drand/tlock) illustrates a concrete future-beacon approach to time-targeted encryption. It is not integrated here and is not evidence that an already distributed ciphertext can be revoked after a check-in. The [Intel SGX overview](https://www.intel.com/content/www/us/en/developer/tools/software-guard-extensions/overview.html) describes hardware memory isolation; it does not establish Otherwise policy correctness, trusted UTC, anti-rollback or an infallible hardware boundary.

An arbitrary real-world obligation—particularly non-observation of a human check-in—requires some trustworthy observation and timing model. A signature certifies who asserted a fact, not whether that fact is objectively true. Stronger cryptography may change who must collude or which capability is unavailable before release; it does not remove the need to specify those roots of trust.

The current answer is deliberately narrow and falsifiable: SaaS-only access to this generation's **public** projection does not supply a creator signature or enough key shares. A sufficiently colluding static-share quorum still decrypts early. A compromised trusted creator client can expose the entire key/seed during local creation. Previously exposed 0.4 material remains exposed. None of those limitations is solved by adding witnesses, moving hosts or adopting another transport.
